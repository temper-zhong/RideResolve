# RideResolve 方案变更申请：腾讯云 ADP 混合架构

> 变更编号：CR-001  
> 状态：待项目负责人批准，当前禁止实施公网部署或 ADP 工具导入  
> 基线：`项目实施总方案.md` v1.5  
> 申请版本：1.1（已吸收严格审查意见；仍非正式实施基线）  
> 提出日期：2026-10-07

## 1. 申请结论

申请把原方案中的“本地 Python 直接完成三个 Agent 的模型调用与编排”调整为受控混合架构：

- 腾讯云 ADP 负责 Rider Advocate、Driver Advocate、Judge 三个 Agent 的模型运行和可视化调用轨迹；
- Python 服务继续独占案件快照、证据、政策、结构校验、退款计算、业务门禁、状态机和 Decision Delta；
- ADP 只能通过三个只读、白名单工具接口读取必要数据；现有实现仅验证了“请求参数对应快照”的数据范围检查，尚未实现运行级授权隔离，后者是实验开始前必须补齐并验证的硬门槛；
- Streamlit 单页 Demo、两类纠纷、三 Agent 数量、DEMO_POLICY_V1、Gate B、Gate C 和所有确定性业务规则保持不变；
- ADP 只给出建议，不能执行退款、修改证据、决定最终案件状态或绕过 Python 门禁。

该变更不是将确定性裁决逻辑迁移到 ADP，也不是新增 Agent、RAG、真实支付或真实用户数据。

## 2. 原方案

原方案由本地 Python 负责：

1. 调用 OpenAI-compatible 模型接口；
2. 驱动 Rider、Driver、Judge 的运行顺序；
3. 验证工具名称和参数并在本地执行查询；
4. 校验模型输出；
5. 执行业务门禁、状态机和 Decision Delta；
6. 通过 Streamlit 展示结果。

原方案的优点是控制力强、依赖少、可离线复现；但前提是已经具备可调用、支持所需交互方式的模型 API，并需要自行实现 Agent 循环、工具回传、运行轨迹和异常处理。

## 3. 变更诱因与事实依据

### 3.1 原方案的模型通道尚未完成验证

基线文件把 Gate A 标记为“缺少模型服务配置”。当前仍没有经验证的 `LLM_BASE_URL + LLM_API_KEY + LLM_MODEL` 本地调用链，也尚未证明该通道能够稳定完成工具选择、结果回传和结构化输出。

这意味着继续原路线仍需先解决模型接入，再开发和验证完整 Agent 调用循环，Gate A 的核心风险尚未消除。

### 3.2 ADP 三 Agent 工作流已经产生真实模型运行证据

当前已在腾讯云 ADP 中建立 Rider Advocate、Driver Advocate 和 Judge，并完成一次真实模型顺序运行。已有运行记录表明：

- 三个 Agent 均被实际调用；
- 能生成带 `evidence_id`、`rule_id` 和建议行动的结构化内容；
- 该次证据直灌工作流约 24 秒完成；这个数据只证明一次已有运行的耗时，不能证明加入工具调用、跨系统网络和重试后仍满足 120 秒整案上限；
- ADP 能展示每个节点的耗时、输入、输出和 Token 消耗。

虽然本次运行把证据直接放入输入，尚不满足 Gate A 的“自主选择证据查询”，但它已经降低了“模型是否能完成三角色编排和结构化论证”的不确定性。

### 3.3 当前最短缺口已经从“模型是否可用”变为“Agent 如何安全取证”

要通过 Gate A，必须形成：

```text
案件摘要 → Agent 自主选择工具 → 程序校验并查询
→ 工具结果回传 Agent → Agent 引用真实 evidence_id
```

ADP 是云端执行环境，不能直接读取本机 `localhost`、本地 JSON 或 Python 函数。因此，如果保留 ADP 作为 Agent 编排层，就必须提供一个 ADP 可以访问的受控工具入口。公网 HTTPS 是实现这种云端到工具层调用的常见传输方式，不是业务目标本身。

### 3.4 已有工程资产使混合路线具有现实可行性

目前已经存在并通过本地测试的只读工具层、合成案件存储和 OpenAPI Schema，覆盖：

- `get_case_snapshot`；
- `get_trip_evidence`；
- `get_policy_rules`；
- API Key 鉴权；
- 根据请求中的 `case_id + case_version` 读取对应快照，并限制返回该快照成员证据；
- 非法参数和 prompt-injection 风格输入拒绝；
- RD-004 和 NS-002 两类确定性结果。

现有实现的边界必须同时明确：单一 API Key 尚未把授权限制到一次指定运行或指定案件；知道其他合成案件标识的持钥调用者仍可能请求其他案件；`get_policy_rules` 也尚未通过运行上下文绑定政策版本；当前没有限流和结构化工具审计。这些能力只能称为待实验的基础资产，不能称为已完成的运行级隔离。

因此申请变更不是从零引入另一套平台，而是考虑复用已经验证的 ADP 工作流和只读工具资产，缩短 Gate A 的剩余路径；是否真的更短，必须由限时实验而不是文档推断证明。

### 3.5 比赛演示需要可观察的三 Agent 协作证据

总方案要求“Agent 及工具协作过程在 UI 中可观察”。ADP 已能原生展示三个 Agent 节点、执行顺序、输入输出、耗时和 Token 使用，可作为开发和评审留痕。Python/Streamlit 仍需展示产品级结果，但无需重复制造一套同等完整的云端 Agent 调试界面。

## 4. 拟修改内容

### 4.1 编排责任

原方案：Python 直接编排三个模型角色。  
拟修改：ADP 运行三个 Agent；Python 通过受控入口提供只读工具，并在 ADP 返回建议后执行最终校验。

### 4.2 工具访问方式

原方案：模型产生工具请求，由同一 Python 进程验证并调用本地函数。  
拟修改：ADP 产生工具请求，通过 HTTPS 调用 Python 只读工具 API；API 对名称、参数、运行凭据、案件版本和返回范围进行验证。实验不得只依赖一个可遍历全部案件的长期 API Key，必须增加短期且不可猜测的 `run_id/run_token`，由服务端运行清单绑定唯一 `case_id + case_version + policy_version + expires_at`。工具接口从运行清单解析案件和政策，不能接受模型任意改写授权范围。

### 4.3 模型配置

原方案：使用 `LLM_BASE_URL / LLM_API_KEY / LLM_MODEL`。  
拟修改：模型与角色配置保存在 ADP；Python 保存 ADP 应用调用凭据和工具服务密钥，所有密钥仍只允许位于 Secret 或本地 `.env`。

### 4.4 日志与演示

原方案：Python 自行记录全部模型与工具轨迹。  
拟修改：ADP 保存 Agent 节点轨迹，Python 保存工具审计、确定性验证、状态和 Delta 轨迹；Streamlit 将二者整理为产品展示。可观察性本身不等于可验证性：同一个不可猜测 `run_id` 必须贯穿 ADP 初始输入、每次工具请求、End 单层 JSON、Python 门禁结果和最终运行记录。Python 工具审计至少记录 `run_id`、请求 ID、接口名、授权映射的案件/版本/政策、参数摘要、返回 ID、开始与结束时间、耗时、状态及错误类型，并能与 ADP 导出的节点轨迹逐项对应。

## 5. 明确保持不变的内容

以下内容不因本申请改变：

- 仍然只有 Rider Advocate、Driver Advocate、Judge 三个 Agent；
- Route Deviation 与 No-Show Charge 两类纠纷必须完整支持；
- 两个 Advocate 必须独立选择查询，不得接收预写论证；
- Judge 只能建议，最终状态由 Python 确定；
- 证据、政策、退款金额和 ID 引用均由 Python 确定性校验；
- `RESOLVED / PENDING_HUMAN_REVIEW / FAILED` 的语义保持不变；
- Decision Delta 仍完全由确定性代码生成；
- 每案最多 7 次模型调用、120 秒整案期限和结构修复上限保持不变；
- 不连接真实支付、地图、用户账户或真实生产数据；
- Streamlit 仍是最终英文单页 Demo；
- Gate A、Gate B、Gate C 的验收条件不得降低。

## 6. 修改后的优势

### 6.1 更快消除 Gate A 的最大未知项

ADP 已证明三个模型角色能实际运行。剩余工作集中在三个只读工具的真实调用与结构化结果校验，比从头实现和调试完整本地 Agent 循环更聚焦。

### 6.2 更强的多 Agent 可观察性

ADP 原生提供节点级输入、输出、耗时和 Token 记录，更容易证明三个 Agent 真实参与，并帮助定位哪一个角色或工具失败。

### 6.3 更适合现场展示和过程留痕

评委可以直观看到 Rider、Driver、Judge 的执行链，而 Python/Streamlit 展示证据、门禁和 Decision Delta。平台轨迹与产品结果形成两层证据。

### 6.4 保留确定性安全核心

混合架构没有把业务决定交给云端 Agent。即使 ADP 产生错误金额、虚构 ID 或非法行动，Python 门禁仍能拒绝输出并进入 `FAILED`，不会把模型建议直接当成最终裁决。

### 6.5 降低自建编排界面的工作量

ADP 承担 Agent 调试视图、节点状态和基础编排，可减少重复开发内部调试页面的时间，把有限工时集中在政策、验证、Delta 和最终 Demo。

### 6.6 形成更清晰的职责分层

修改后可以清楚说明：

```text
ADP：生成论证和建议
Python：保存可信事实、执行规则、决定状态
Streamlit：向评委解释过程和结果
```

这比让一个模型平台同时掌握事实、规则和最终状态更安全，也比在本地同时自建模型平台、工具层和 UI 更节省时间。

## 7. 相比原方案的代价与风险

该变更并非无条件更优，必须正视以下代价：

1. **新增部署面**：只读工具服务必须被 ADP 访问，会增加 HTTPS、域名或网关配置工作。
2. **新增网络故障点**：ADP 到工具服务的超时、限流或平台异常可能使整案失败。
3. **密钥管理更复杂**：需要分别管理 ADP 应用凭据和工具 API Key。
4. **平台依赖增强**：ADP 接口或编排行为变化会影响复现能力。
5. **截止时间与次数控制更难**：必须验证 ADP 调用、工具调用和重试能够共同遵守 120 秒限制及 7 次模型调用上限。此前 24 秒的证据直灌结果不能证明这一点；如果 ADP 不能提供足够的节点/调用数据，就不能宣称该项通过。
6. **输出绑定仍需修复**：当前 Judge 内容存在 JSON 字符串嵌套现象，工作流 End 节点还没有形成稳定的最终输出契约。
7. **当前 Gate A 仍未通过**：已有 ADP 运行是“证据直灌”冒烟测试，不能替代真实自主工具调用。
8. **公网并不自动更安全**：工具 API 必须坚持只读、最小字段、运行级授权、限流、结构化审计、日志脱敏和合成数据；不得暴露文件系统或通用执行能力。现有实现还没有完成运行级授权、限流和结构化审计。
9. **OpenAPI 地址可能被错误生成**：现有动态 `/openapi.json` 会依据请求 Host 生成地址并可能出现 `http://`。实验导入的固定 Schema 必须显式指向经过控制的 `https://` 地址，不能直接采用未经核对的动态地址。

## 8. 风险控制条件

只有同时满足以下条件，混合路线才允许继续：

- 工具 API 只暴露三个白名单查询，不提供写入或通用代码执行；
- 所有工具请求必须携带有效服务认证和短期运行凭据；
- 服务端运行清单必须把不可猜测的 `run_id/run_token` 绑定唯一 `case_id + case_version + policy_version + expires_at`；三个工具均只能从该运行清单解析数据范围，不能由模型参数扩大范围；
- 必须设置按服务密钥和运行标识计算的请求次数上限；超限请求必须拒绝并写入审计；
- 仅使用明确标记的合成数据；
- ADP 的工具说明不得包含密钥；
- Python 对 ADP 最终输出进行 Pydantic 校验、引用校验、政策校验和退款上限校验；
- 同一 `run_id` 必须贯穿 ADP 输入、工具审计、End 单层 JSON 和 Python 门禁结果；
- 完整运行必须形成可导出的结构化工具审计，记录耗时、调用次数、请求/返回 ID 和失败类型，并与 ADP 节点轨迹相互核对；
- 导入 ADP 的 OpenAPI Schema 必须显式指向受控 HTTPS 地址；不得依据未经校验的请求 Host 动态生成生产导入地址；
- 不能满足 120 秒、7 次调用或输出契约时，不得宣布 Gate A 通过；
- 不把 ADP 自评置信度用作业务放行条件；
- 不因接入 ADP 删除任何 Gate B/Gate C 测试。

## 9. 批准后的限时验证方案

该变更建议设置严格止损，不进行开放式平台迁移。

### 第一阶段：最多 3 小时

1. 在本地补齐短期运行凭据、服务端运行清单、请求次数上限和结构化工具审计，并通过测试；
2. 生成显式指向受控 HTTPS 地址的固定 OpenAPI Schema，禁止把动态 Host 结果直接导入 ADP；
3. 将只读工具服务部署到受控测试地址；
4. 在 ADP 中只导入三个工具；
5. 使用同一 `run_id` 运行一个 Route Deviation 合成案件；
6. 验证 Rider 与 Driver 是否各自独立选择工具、收到真实工具回传并引用真实 `evidence_id`；
7. 验证非法参数、错误密钥、过期/错案运行凭据、超限请求和注入文本会被拒绝；
8. 将 ADP 节点轨迹、Python 工具审计、End 单层 JSON 和 Python 门禁结果按 `run_id` 关联，核算总耗时与模型调用次数。

### 通过标准

- 完整满足原 Gate A 七项条件；
- Rider 与 Driver 的工具选择、工具回传和引用轨迹彼此独立且可按同一 `run_id` 验证；
- Judge 结果能够从 End 节点以单层 JSON 返回；
- 总耗时不超过 120 秒；
- 有足够的 ADP 与 Python 记录证明模型调用总数不超过 7 次；无法证明等同于未通过；
- Python 门禁能够接收并验证结果；
- 失败时能明确进入 `FAILED`，而不是生成伪裁决。

### 止损条件

出现任一情况立即停止混合路线：

- 3 小时内无法完成一次真实工具调用闭环；
- ADP 无法稳定传递结构化结果或真实 ID；
- 无法将工具权限绑定到指定运行、案件版本和政策版本；
- 无法可靠关联 ADP 轨迹、工具审计、End 输出与 Python 门禁结果；
- 无法用记录证明调用次数与整案耗时；
- End 节点无法稳定返回单层 JSON；
- 部署工作明显挤占 Gate C、Streamlit 或两类纠纷的必须工时。

## 10. 回滚方案

若验证失败：

1. 停止并下线测试工具入口，撤销对应密钥；
2. 保留纯 Python 工具函数和测试，删除或禁用 HTTP/OpenAPI 适配层；
3. 将项目状态恢复为“原本地 Python 编排路线待继续实施”，而不是声称切换到一个已经跑通的备份；
4. 重新完成原路线尚未解决的模型 API 接入、Agent 循环和 Gate A 验证；
5. 在模型 API 可用前，ADP 只能作为开发过程留痕，不能被描述为本地运行时的已验证模型端点；
6. 按原 Gate A 的受限 JSON 工具协议继续验证；
7. 不修改 Gate B、Gate C、案例、政策或 Streamlit 交付范围。

该回滚不损失现有确定性政策、证据模型、案例数据和测试资产，但会重新暴露“本地模型接口尚未验证”的原始阻塞，因此回滚是恢复原基线和待办，并非立即可用的热备切换。

## 11. 变更收益判断

本变更值得批准的核心理由不是“云端比本地先进”，而是当前已有可运行的 ADP 三 Agent 工作流，原方案的模型 API 仍未完成验证，并且现有只读工具层已经就绪。在严格保留 Python 确定性控制权、设置 3 小时止损和完整回滚的前提下，混合路线有机会用更短路径完成 Gate A，并提供更清楚的三 Agent 调用证据。

如果不能接受公网测试入口、平台依赖或额外密钥管理，则不应批准本变更，应继续执行原本地 Python 编排方案。
